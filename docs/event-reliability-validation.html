Compost Heroes: Event reliability validation

Completed 1 October 2026 · Development workspace and database only

Result: both requested scenarios passed. Four tables / 16 guests and eight tables / 32 guests remained fully occupied through the active tests. There were 857 successful API requests in total, zero HTTP errors, zero request timeouts, and zero other request errors. No lost updates, cross-table contamination or deadlocks were observed by these checks.

No production database queries or production load/concurrency tests were run. This work made no publishing or deployment-setting changes and left the mockup sandbox untouched. No shared-gameplay architecture/UI migration, Redis or distributed realtime infrastructure was introduced.

1. Exact changes

  1. Lightweight presence. A routine heartbeat now performs one atomic presence update without the game mutation lock. The statement resolves the Event code, token, current token/seat indexes and game JSON player identity together. A removed or stale seat cannot refresh another participant. Only a meaningful presence transition queues a detail push. Jittered timers and online/visibility triggers reduce synchronized check-ins; the 10-second sweep retains the 45-second disconnect threshold and retries missed intervals after database failures.
  2. Held-client locking. Locked Event and game work passes the held database client through authorization, state, token, seat, readiness and persistence helpers. Multi-table controls and transfers acquire sorted game locks on one connection rather than one connection per table. Join transactions release their client before building the response detail. The pool maximum remains 10. Ready still holds the game lock and rejects a transfer race if its refreshed seat belongs to a different game.
  3. Bounded contention and safe retries. Connection acquisition is bounded at 5 seconds, lock waits at 2 seconds and statements at 5 seconds. Busy responses are sanitized and recoverable. A notApplied: true claim is made only when no write was started or rollback is proven; ambiguous writes are not labeled safe to repeat. Client backoff is bounded and limited to safe reads, presence, ready, or an explicit not-applied response. Gameplay is not blindly replayed. Failed unlocks/rollbacks destroy the client; detached cleanup failures are observed rather than becoming unhandled rejections.
  4. Dashboard updates. Detail pushes are coalesced over approximately 350 ms. Host tokens are loaded in one query rather than one query per table. The dashboard applies validated SSE snapshots directly to its auth-scoped query cache, preserving host credentials without a GET on every push. In-flight old GETs are cancelled and cannot overwrite a newer SSE snapshot. A 10-second fallback read and fresh single-use stream tickets preserve recovery.
  5. Readiness. HTTP starts listening before migrations and card initialization. Liveness remains accessible during startup; readiness and product routes stay unavailable until initialization succeeds. Readiness then performs a short, bounded database probe, so an exhausted pool cannot report healthy. Public health returns status only. Pool total/idle/waiting and recent acquisition timings require the existing x-admin-key.
  6. Cache correctness. Durable writes/commits precede cache publication. State snapshots are copied at cache ingress and egress. In-flight generation guards prevent late reads from replacing newer state or resurrecting deleted entries; unknown-game token resolution uses an epoch-bounded reread through the same client. Finished snapshots expire after one hour and idle non-Event snapshots after 24 hours. A rotating 15-minute sweep inspects bounded batches of 250 state and 250 token entries. Waiting and in-progress Event games are protected. Admin game deletion invalidates associated caches.
  7. Sandbox preservation and final validation. The mockup sandbox was left untouched. Reusable A/B load scenarios, strict target checks, guarded cleanup, path-resolution tests and these instructions/results were saved in the repository.

2. Before/after concurrency evidence

The unchanged-code baseline launched 16 simultaneous joins across four tables. All 16 reached their 8-second deadline. A subsequent rooms read still failed to respond within 2 seconds, while the old health route returned HTTP 200 in 42 ms. The PostgreSQL observer saw ten idle connections and no active SQL or database lock waiters. Together with the audited nested checkout path, this identifies application-pool starvation rather than proving a PostgreSQL deadlock.

The identical initial burst passed after the held-client fix before timeout configuration was introduced: 106 successful requests, zero errors/timeouts, presence p95 203.5 ms and action p95 26.8 ms. That earlier harness removed one guest, so it is evidence for the lock fix, not the final full-occupancy result. The expanded final scenarios below retain all 16/32 seats by joining a replacement after the removal test.

Eliminated failure paths include nested connection acquisition while retaining game/join clients, inconsistent multi-game lock ordering, readying a transferred seat under the wrong lock, separately resolved presence identity, failed-write cache publication, stale cache resurrection, falsely healthy startup/pool exhaustion and unobserved unlock-release failures.

  • All 21 backend unit/route test files passed, including the added database-safeguard, presence, dashboard, startup-readiness and cache tests. Existing gameplay, privacy, decision-coverage, facilitated kick, Event, auth/session and stream-ticket tests remained green.
  • Focused frontend presence tests and a real QueryClient integration passed: cancellation of an in-flight detail GET, late-GET rejection, direct SSE application, preserved host tokens and mismatched-Event rejection. Auth-scoped stream cleanup guards remain active.
  • Shared-library, API, web and scripts typechecks passed. The scripts path/realpath guard test passed. Final focused architecture review found the reported blockers closed.
  • Intentional development-database faults were measured separately: exhausted acquisition returned sanitized 503 after about 5,009 ms and recovered; advisory contention stopped after about 2,006 ms with notApplied: true and no mutation callback; a long statement was cancelled after about 5,001 ms with SQLSTATE 57014. These are actual fault measurements, not fabricated harness timings. The fault checks did not write game rows.
  • Scoped cleanup verified and removed generated Events, table links, seats, games, tokens, analytics, synthetic accounts and sessions. Both final manifests passed zero-residual assertions. Raw credential-free reports and manifests remain locally under ignored scripts/results/.
  • The restarted development API passed public readiness/liveness checks. A fresh application preview rendered successfully. No broad browser workshop benchmark was substituted for the measured API/SSE scenarios.

5. Reusable commands

Start the existing development API workflow normally, verify it uses the development database, then run from the workspace root:

NODE_ENV=development pnpm --filter @workspace/scripts run event:reliability -- --scenario A --confirm-development-database
NODE_ENV=development pnpm --filter @workspace/scripts run event:reliability -- --scenario B --confirm-development-database

# Use the exact manifest printed by that run:
NODE_ENV=development pnpm --filter @workspace/scripts run event:reliability -- --cleanup scripts/results/<run>.fixtures.json --confirm-development-database

See scripts/DEVELOPMENT_EVENT_LOADTEST.md for safety gates, deadlines, output format and the explicit isolated staging-VM option. The script refuses normal published targets; staging reruns must still use a confirmed development database and local API, never production. It does not start workflows or publish. Fixture cleanup rejects symlink/path escapes and verifies ownership before deleting anything.

6. Remaining concerns and VM recommendation

Recommend a dedicated Reserved VM for live 32-player workshops, using an available dedicated tier with at least 1 vCPU / 4 GiB as the initial staging candidate. The reason is predictable CPU availability and operational headroom, not evidence that a shared VM failed: no Reserved VM was benchmarked here. A shared tier remains a possible lower-cost choice only after the same checks pass on that isolated staging configuration.

  • Development-environment timings are preliminary. Repeat A and B on the intended isolated staging VM before treating these as VM capacity results.
  • These approximately one-minute scenarios are not a multi-day soak test or a capacity claim above 32 guests. CPU/RAM utilization, real venue Wi-Fi and browser paint latency were not benchmarked.
  • Waiting/in-progress Event caches deliberately cannot be evicted. Forgotten unfinished Events should be ended; long-running memory behavior deserves a later soak check.
  • The design intentionally remains single-instance. Horizontal scaling needs separate realtime/cache coordination work, outside this phase.
  • Ambiguous write/commit failures intentionally do not trigger automatic gameplay replay. Players should refresh authoritative state before manually retrying.
  • Multi-table controls retain per-table commit behavior: if a later database operation fails, earlier tables may already have changed. Such an error is not claimed to be wholly unapplied; refresh the authoritative detail before retrying.
