---
name: Compost Heroes conventions
description: Durable architectural decisions for the Compost Heroes game
---

- **Online and Facilitated share multiplayer transport and per-viewer serialization, but not facilitator powers.** **Why:** separate multiplayer stacks would drift, while ordinary Online hosts must have no facilitator oversight or access to private decisions. **How to apply:** include both in remote identity/update handling, but require the exact Facilitated mode and its approved host for facilitator-only controls.
- **Hidden information must be redacted per viewer, not per zone.** **Why:** decision prompts and options can carry hand-derived card identities even when hands themselves are hidden — a past review caught this leak. **How to apply:** when adding any new field to the broadcast game state, ask whether a non-owner viewer could infer hidden cards from it.
- **Browser caches are part of the hidden-information boundary.** **Why:** correctly redacted responses can still expose a previous seat's private details when a game-only cache is reused for another viewer. **How to apply:** isolate cached snapshots by credential, reject obsolete responses, and never use collision-prone short hashes as viewer identities.
- **Player names are untrusted input when interpreting legacy logs.** **Why:** names containing phrases such as “from compost” or transfer grammar can make a hidden hand operation look public. **How to apply:** use fixed conservative summaries for ambiguous legacy lines; new effect copy should come from structured facts rather than inferred sentence fragments.
- **Effect summaries need operation provenance across both human and bot execution.** **Why:** zone differences cannot distinguish a public discard choice from a random reshuffle draw, or preserve a discard followed by redrawing the same instance; naming an inferred discard pick can expose a hidden hand. A later choice owner also is not necessarily the original card actor. **How to apply:** capture transient operations over the complete announcement interval, exclude played-card costs, require explicit selection provenance before naming discard-to-hand gains, and carry the original actor/verb through decision chains. Keep traces out of saved and serialized game state.
- **Game deletion must invalidate live cached state and credentials as well as persisted rows.** **Why:** database-only deletion left a synthetic room reachable in the running server even after its row was gone. **How to apply:** verify old links lose access after deletion; a successful database delete alone does not prove runtime cleanup.
- **Mode boundaries are product requirements, not a reason to fork the game UI again.** **Why:** the creator wants improvements available consistently without changing each mode's identity, privacy, or control rules. **How to apply:** express differences as capabilities in shared components. The creator requires advance notice before removing the older local facilitator mode.
- **Preserve pending effects until their actual choice owners finish, regardless of who owns the main turn.** **Why:** a bot's effect can pass through another bot and then a human; clearing a pending choice to advance the starting bot silently skips choices and exchanges. **How to apply:** automate only bot-owned choices, wait for human owners, and reapply shared-device handoff privacy when the decision actor changes.
- **Never put user sign-in tokens in shared URLs; seat links are distinct from account sessions.** **Why:** a copied account-token link grants account access, whereas facilitated guests need only their game seat credentials. **How to apply:** sign in through the account form for host/Online access, and share only the game seat token in a facilitated table link; do not reintroduce `?ut=` account-token import.
- **Facilitator assist controls (pause and step-in resolve) live on host-gated endpoints; step-in resolves auto-pick server-side.** **Why:** showing a host another player's decision options would leak hand-derived cards; picking a sensible option on the server (skip when optional, first option otherwise) keeps hidden info intact. **How to apply:** new facilitator powers require both the correct host token and the approved creator account; never surface redacted decision options to the host client. Ordinary Online player-to-player nudges are not facilitator powers.
- **The API contract is spec-first.** **Why:** the spec once lagged the server, forcing type escapes in the frontend. **How to apply:** change the OpenAPI spec and regenerate clients in the same task as any server response-shape change.
- **Keep the requested reliability model: no new polling, no per-player writes, and gameplay mutations under the game lock.** **Why:** the creator explicitly requires these constraints. **How to apply:** preserve them when adding timer, presence or table features.

## Registration rules (Aug 2026)
- Lobby "/" is ungated; Pass & Play needs no account. Online requires sign-in — enforced server-side (create/join/claim take `userToken`, validated via userStore) AND client-side (AppGate gates /game/:id only when game mode is online; `?signin=1` forces the gate UI from ungated pages).
- Facilitated: participants join with session code (= gameId) + name only via the lobby's "Have a code?" screen → /game/:code/table; hosting requires an account.
**Why:** product policy from Danny's landing-page spec — zero friction for participants, accountability for hosts/online play.

## Facilitator session management
- Facilitated sessions carry `facilitatorId` (account id), `label`, `createdAt`, `endedAt` in GameState; `storeGame` stamps `endedAt` on any `game_over`. Resets must preserve this metadata or the room drops off the creator's dashboard.
- New facilitated rooms reserve player index -1 for a non-playing facilitator; older rooms keep their seated host at index 0. **Why:** the facilitator should manage a full table without taking a playing seat, but existing sessions must continue to work. **How to apply:** use the room's host/spectator flag for host gates and seat counts; protect legacy seat zero from participant moves; host recovery must locate the appropriate token from either kind of room.
- A waiting-room transfer moves the participant's credential to the destination, so a missed live redirect must be recoverable from durable token ownership; resets must preserve player IDs. **Why:** SSE events can be missed, and changing a player's ID while retaining their token breaks identity checks. **How to apply:** treat seat credentials and IDs as part of the same identity when reordering, transferring, leaving, or resetting; never assign a stale token to another person's seat.
- Participant questions are facilitator-directed: `serializeState` redacts them so non-host viewers only see their own. Any new facilitator-directed field must be redacted the same way (public GET + SSE both go through serializeState).
- After `game_over` (natural or host-ended), all gameplay/question/message mutations return 409; only `reset_game` is allowed.
- **In-progress facilitator removal is a bot handoff, not deletion of the seat.** **Why:** an inactive participant should lose access immediately without discarding their cards, pile, and turn progress or leaving the table stalled; waiting-room removal can free the unplayed seat instead. **How to apply:** preserve live player identity and game state, revoke the removed credential, and let the bot finish its turn without skipping a decision owned by another human.
