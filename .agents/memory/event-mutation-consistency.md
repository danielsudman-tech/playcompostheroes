---
name: Event mutation consistency
description: Why event-table gameplay writes must coordinate with joins, and why generic schema push is unsafe here
---

- **All mutations of an event-linked game must coordinate across the event and ordinary game routes using a database-level per-game lock.** **Why:** the state is stored as one JSON document, so a concurrent guest join and a game start, end, or action can otherwise overwrite each other despite route-local locks or in-memory coordination. **How to apply:** acquire the shared lock and reload durable state before changing an event table; keep event seat, token, and state changes in sync when guests leave or transfer.
- **Treat generic development schema push prompts as unsafe for this project's legacy raw-SQL game tables.** **Why:** Drizzle proposed a rename involving unrelated existing tables when adding the event tables, which could have damaged persistent game data. **How to apply:** review proposed changes, add only intended new tables and indexes to development, and use the managed Publish schema flow for production; never force a broad push just to create event tables.
- **Every helper invoked while retaining a game lock or Event join client must use that same client; release it before detached detail work.** **Why:** nested pool checkout starved a 16-guest burst while PostgreSQL showed idle connections and no lock waiters. Increasing the pool or turning hangs into timeout errors would only hide the cause. **How to apply:** audit the entire helper chain, including authorization, metadata and persistence; validate successful full-occupancy bursts, not merely finite failures.
- **Readiness must remain reachable while startup initialization is blocked.** **Why:** awaiting migrations before listening prevents an external health check from distinguishing an initializing or failed service from an unreachable one. **How to apply:** listen first, keep liveness public, and gate readiness/product traffic until all initialization succeeds.
- **Use a narrow promise-query interface plus an explicit release signature for held PostgreSQL clients.** **Why:** node-postgres overloads include callback-based connection acquisition and submittable queries; deriving clients with `ReturnType` or intersecting the native query overloads can infer `void` or non-promise results. **How to apply:** type helper boundaries explicitly rather than deriving their contract from the last overload.
- **Perform deletion's runtime invalidation after confirmed commit but before leaving the lock callback.** **Why:** advisory unlock can fail after a successful commit; cleanup placed after the outer lock helper then never runs, leaving deleted games and credentials cached. **How to apply:** clear caches and terminate affected streams inside the successful transaction callback's post-commit path, before lock release; test rollback and committed-unlock-failure separately.
